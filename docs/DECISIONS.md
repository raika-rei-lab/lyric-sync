## 1. 開発方針（最重要）

**最優先は本人の MV 制作環境で快適に使えること**です。一般公開は副次的な目標です。

### 対象環境（基準）

| 項目 | 値 |
| --- | --- |
| GPU | RTX 2060 6GB |
| RAM | 64GB |
| OS | Windows 11 |
| ブラウザ | Chrome / Edge |
| 実行 | WebGPU（主経路）、`medium` モデルが基本 |

### 開発優先順位（合意済み）

1. **歌詞の同期精度**（整列率・時刻の妥当性）
2. **手動補正の操作性**（UI の直感さ）
3. **SRT / LRC の実用性**（書き出したファイルがそのまま使えるか）

### 明示的に**対象外**としたこと

- 低スペック PC への最適化
- スマートフォン対応（README でも「非推奨」と明記）
- WASM 前提の軽量化（スレッド数・軽量 dtype・モバイル UI）
- **モデル関連の改善**（当初の検討は終えて合意済み）

### 作業の進め方に関する希望

- **実装の明示的な依頼がない限り、コード変更をしない**（質問・方針共有は質問で返す）
- 詳細な修正より**ダウンロードしたファイルを直接編集する**方が 선호される場面がある
  （例: 漢字→ひらがな表記、アドリブ繰り返し、コーラス追加）
  → そのような機能は優先度を上げて実装しない
- ドキュメント・スクリーンショット・注記の正確性を重視する
- push は本人が行う（AI は commit までを担当し、push は行わない）

## 2. ツールの概要

**Lyric Sync** — ブラウザだけで完結する歌詞同期ツール。
AI 生成音楽（Suno など）の**音声と歌詞テキスト**から各単語の再生時刻を推定し、
MV 制作で使える 7 形式の字幕・歌詞ファイルを出力する。

- サーバー不要・API キー不要・無料
- **音声も歌詞もブラウザの外に送信されない**（通信はモデルの DL のみ。初回約1.6GB）
- MIT ライセンス / GitHub: <https://github.com/raika-rei-lab/lyric-sync>
- デモ: <https://raika-rei-lab.github.io/lyric-sync/>

### 処理の流れ

```
音声 ──Web Audio──> 16kHz モノラル PCM
                          │
        Whisper (ONNX) return_timestamps:'word'
                          │
        Needleman-Wunsch で歌詞トークンと整列
                          │
        行・単語タイムスタンプ → LRC / TTML / SRT / VTT / JSON
```

## 3. 実測データ（すべて実測値）

### 認識精度

同一楽曲（日本語ボーカル 3分20秒）での比較。

| モデル | 解析時間 | RTF | 整列率 | 一致精度 | 未整列 |
| --- | --- | --- | --- | --- | --- |
| `small` | 98.5s | 0.51 | 86.5% | 98.2% | 44 / 327 語 |
| **`medium`（既定）** | 145.4s | 0.75 | **96.0%** | 98.7% | **13 / 327 語** |

`small` → `medium` で **15 語を救い、壊れた語は 0**（`node test/diff-models.mjs` で検証可能）。
`medium` の残り13語は内訳が判明済みで、うち **8 語が同音異字**（モデルを上げても直らない）。

### モデルのダウンロード量（**実測**：モデルファイルの実サイズ）

| モデル | WebGPU | WASM |
| --- | --- | --- |
| base | 約200MB | 約70MB |
| small | 約560MB | 約240MB |
| medium | 約1.6GB | 約940MB |
| turbo | 約2.7GB | 約1.0GB |

**GPU メモリ（VRAM）使用量は推定値**であり、実測していない。
WebGPU では fp32 encoder を読み込むため WASM（q8）より大きく、実行時にはさらにメモリを使う。
6GB 未満の GPU では非推奨。

### アルゴリズム改善の実績（いずれも fixture で実測）

| 改善 | 効果 |
| --- | --- |
| CJK を両側とも1文字単位に展開して整列 | 83.2% → **86.5%** |
| DTW 巨大スパン補正（イントロ間奏の吸収） | 1行目の開始 0.00s → 13.5s に修正 |
| DTW 退化スパン補正（長さゼロの連続） | 3箇所・28語を修復 |
| 間奏（2.5秒超の空白）への補間回避 | `祈り` が 118.76s → 124.84s に修正 |

## 4. 守るべき技術的制約（壊すと壊れる）

| # | 制約 | 理由 |
| --- | --- | --- |
| **1** | `chunk_length_s` は **29 固定** | 30 にすると `_timestamped` モデルの時刻が全滅する（transformers.js #1357） |
| **2** | WebGPU では **1曲ごとにパイプラインを破棄**して作り直す | 30秒チャンク毎の GPU メモリリーク対策（transformers.js #1739、推定約650MB/チャンク） |
| **3** | `base` の base パスは `/` のまま | デフォルトで `/lyric-sync/` にすると既存の E2E（`/` 前提）が壊れる。Pages 用ビルドだけ `--base` を渡す |
| **4** | Node 版 transformers.js は **cpu / cuda のみ** | `wasm` は使えない（Node では `cpu` を使う） |
| **5** | `asr-*-worker.js` は `new URL()` で生成 | Vite がビルド時にパスを解決するため、`base` が自動で反映される |

## 5. 過去の重要な判断（理由つき）

| 判断 | 理由 |
| --- | --- |
| `small` を推奨から外し `medium` を既定に | 実測で 15 語改善・破壊ゼロだったため。turbo は 6GB GPU で VRAM が約7.2GB 必要（推定）になる |
| `turbo` は残置 | CPU での短い音声では 100% で動作確認済み。ただし WebGPU での長時間動作は未検証のため、注記付きで選択可能に残す |
| かな正規化（kuroshiro）を**採用しない** | 1文字ずつ文脈無しでかな化すると壊れる（例: 2文字の語を1文字ずつ処理すると片方だけ漢字のまま残る）。実測で整列率が 86.5% → **63.6% に低下**。辞書は 17MB |
| SRT は「1行最大文字数」で語境界分割 | 文字の切れ目で折り返すと日本語として不自然になるためです |
| ツール名を `Suno Lyric Sync` → `Lyric Sync` | ツールは Suno に依存しないため。説明文中の「Suno などの AI 生成音楽」は維持 |
| 履歴を作り直して公開 | 初期コミットに含めてはいけない情報が混入していたため。push 前に `git checkout --orphan` で 1コミット化し、`git reflog expire` と `git gc --prune=now` で旧オブジェクトを消去した |

## 6. 既知の制約・未対応

- **歌唱音声は ASR が苦手**（同音異字・伴奏・抑揚）。人手での仕上げが前提（実測でも 13/327 語）
- **言語の自動判定は歌唱音声で失敗する**。必ず明示指定する（最初のテストで整列率 5% になった原因）
- Safari は**未検証**
- CI（GitHub Actions）は GPU を使わないため **WebGPU の主経路はカバーしていない**（制作時の実機確認がテストになる）
- ボーカル分離（Demucs 等）は入れていない

### ツールとして把握している過去の不具合（すべて修正済み）

| 症状 | 原因 | 状態 |
| --- | --- | --- |
| 語間スペースが1語ずれる | 空白を語の後ろに配置していた | 修正済み |
| 「認識テキスト採用」で英語の語間が消える | 空文字連結を使用していた | 修正済み |
| `prepare-push` でハング | Worker の応答名とリクエスト名が不一致 | 修正済み |
| CI の matrix が効かない | `node-version` を `setup-node` に配列で渡していた | 修正済み |
| `vite preview --base` でアセットが 404 | preview はアセット配信に base を適用しない | `test:pages` は Pages を模した静的サーバを使用 |

## 7. 保留中の機能（優先度付き）

いずれも**明示的に依頼されたときだけ**着手する。

| # | 機能 | 所要 | 備考 |
| --- | --- | --- | --- |
| 1 | **歌詞を編集して再整列**（ASR 再実行なし） | 30分 | テキスト修正が即座に反映される。`state.asrWords` を再利用できます |
| 2 | **波形＋タイムライン UI** | 3〜4時間 | 未整列語を目で見て直せるようにする |
| 3 | **表示テキスト差し替え**（かな化・コーラス追加・反復） | 1.5時間 | 認識テキストで整列したうえで表示だけ差し替える |
| 4 | **文全体版かな正規化** | 3時間＋辞書17MB | 同音異字を自動対応（13 → 5 語）。ブラウザでの辞書読み込みが技術リスク |
| 5 | 複数曲の一括処理 | 1時間 | `finalize.mjs` は単曲前提 |

## 8. 再開時のチェックリスト

新しいセッションで作業を始める前に:

1. **このファイルを読む**（`docs/DECISIONS.md`）
2. **README.md を読む**（現在の仕様・制限）
3. **次のコマンドで現物が動くか確認する**

```bash
cd <このディレクトリ>

npm install
npm run test:unit     # 43項目（モデル不要・即時）
npm run test:e2e      # 35項目（ブラウザ実操作・本番ビルドを preview）
npm run test:pages    # 13項目（GitHub Pages 相当のサブパス検証）

# 実データでの整列効果を確認する場合
node test/exp-align.mjs      # fixture でアルゴリズムの効果比較
node test/diff-models.mjs    # 2つの .debug.json を単語レベルで比較

# ASR を再実行せずに成果物を再生成
node scripts/finalize.mjs 曲名.debug.json 歌詞.txt out/
node scripts/regen-lrc.mjs 曲名.debug.json out/
```

### ファイル構成

```
src/text.js        正規化・トークン分割（英単語 / 日本語 Intl.Segmenter / 韓国語）
src/align.js       Needleman-Wunsch 整列、CJK 文字展開、時刻補間
src/pipeline.js    行構成・メタタグ・オフセット
src/lrc.js         LRC / enhanced LRC / TTML / SRT / VTT / JSON の出力
src/asr-core.js    Whisper 実行＋後処理（巨大スパン・退化スパン補正）
src/asr-worker.js  Web Worker 実行
src/asr.js         Worker 制御・音声デコード（16kHz モノラル化）
src/main.js        UI（表示のみ。ロジックは上記に集約されている）
```
